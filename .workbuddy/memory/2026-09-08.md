## Video Scissors — 新增「多切片 + 拼接」功能

需求:支持多个切片,各自裁剪后拼接成一个输出。

### 改动
- **后端** server.js 新增 `POST /api/trim-multi`:
  - 入参 `{ filename, mode, segments:[{start,end}] }`
  - 逐个切片 ffmpeg 裁剪 → 临时片段 → 写 concat 清单 → `ffmpeg -f concat -safe 0 -i list.txt -c copy` 合并
  - 进度汇总 0–100%(各切片按 (i+frac)/N*90 +1, 拼接 95→99),轮询复用 `/api/status/:jobId`
  - 校验: 空/超 100 切片/模式非法/时间越界/文件缺失;临时片段与清单在 finally 中清理
  - 输出命名 `merged-<ts>-<rand>.mp4`
- **前端** index.html / style.css / app.js:
  - `state.segments` 数组;「把当前选区加入切片」按钮;切片列表(起止/时长/删除/点击回填选区);「合并导出 (N)」按钮(无切片禁用)
  - 导出改为调 `/api/trim-multi`,结果区文案改为「已合并导出」
- **模式策略调整(重要)**: 快速/精确现在都改为重新编码(libx264/aac),不再用流复制:
  - 快速: `preset veryfast, crf 23`;精确: `preset medium, crf 18`;均输出 mp4

### 关键发现(可复用)
- **流复制 `-c copy` + `-ss` 会吸附关键帧,无法做任意时间点精确裁剪**;多片段拼接会把误差放大(实测 testsrc 上切出 4.08s/10.08s,合并成 14.16s 而非 6s)。
- `-ss` 放在 `-i` 前后对 copy 模式都不准;只有重新编码才能得到帧级精确切片,且拼接后总时长才正确(实测每段 3.0s、合并 6.0s)。
- drawtext 滤镜在本机 ffmpeg 会 segfault(字体/fc 问题),测试视频改用纯 testsrc 不带文字叠加。
- 结论: 多切片拼接必须用 re-encode 切片 + concat demuxer `-c copy`(片段已是统一 h264/aac)。

### 验证
- 快速/精确模式多切片(2 段 / 3 段)输出时长均=各切片之和(6.0s)
- 参数校验、单切片走 multi、下载(47705 字节有效)均通过
- 服务重启后运行于 http://localhost:3000(后台任务 YnLAIM)

### 待与用户确认
- 原「快速=无损流复制」已改为「快速转码」,牺牲了无损以换取多切片拼接正确性。如需要无损单片段,可另加仅单片段的流复制分支。

## 修复: ←/→ 步进长度与输入框数值不匹配 + 步进值限制为正整数

### 1. 步进长度不匹配
根因: 原来每次都基于 `video.currentTime` 累加,而浏览器实际落点可能不是请求值(seek 粒度/关键帧),误差会逐次积累,导致实际位移与输入框数值不符。
修复: 引入 `seekTarget`(我们请求的目标位置):
- **暂停时**从 `seekTarget` 累加 → 每次位移严格等于设定值,不受浏览器落点影响;
- **播放时**仍跟随 `currentTime`(自然行为)。
- 通过 `seeked` 事件区分「我们自己触发的 seek」与「外部 seek」(时间轴点击/原生控件),外部 seek 时把 `seekTarget` 置 null 以重新对齐真实播放头;`play` / `loadedmetadata` 也重置。
- 判定用 `stepSeeking` 标志 + 落点与 target 差值 < 0.75s 双保险。

### 2. 步进输入框限制为正整数(不能为 0)
- HTML: `type="number" min="1" max="600" step="1" inputmode="numeric" pattern="[1-9][0-9]*"`(原为 min 0.1 / step 0.5)。
- JS `sanitizeSeekStep()`(绑 `input` 事件): `split('.')[0]` 去小数 → `replace(/[^0-9]/g,'')` 去非数字 → `replace(/^0+/,'')` 去前导零(顺带封死 "0")。
- `blur` 时兜底: 空/非法 → 3;>600 → 600。
- `getSeekStep()` 改用 `parseInt`,`v<1` 回退 3,上限 clamp 600。
- 已单测: 0→3、05→5、007→7、3.5→3、abc→3、999→600、1→1 全部符合预期。

### 复用提示
- 浏览器 seek 落点不等于请求值是常态;凡是「按固定步长跳转」的需求,都应维护自己的目标位置而不是反复读 `currentTime`。
- 数字输入限制整数时,别用 `replace(/[^0-9]/g,'')` 直接吃小数点("3.5"→"35"),先 `split('.')[0]` 截断更自然。

### 二次反馈修复: 空格键失效 + 步进仍不匹配(两者同源)
反馈: 空格切换播放/暂停失效;步进长度仍与输入框数值不符。
根因(同源): keydown 处理器开头有 `if (e.target.tagName === 'INPUT') return;`。用户点过步进输入框后焦点留在 input 里 → 空格和方向键被这段守卫全部吞掉 → 空格无法暂停,视频一直在播放 → 在播放中测步进会因播放推进而看起来「步长不对」。
修复:
1. **空格改为在守卫之前单独处理**: `if (e.key === ' ' && (!inEditable || t === els.seekStepInput))` → 播放/暂停即使在步进输入框聚焦时也生效(数字框不需要空格)。其余快捷键仍遵守「输入时不触发」。
2. **输入框提交后自动失焦**: `change` / `Enter` 时 `sanitizeSeekStep()` + `blur()`,焦点回到页面,方向键恢复。
3. **修正 seekTarget 漂移**: 原逻辑在浏览器落点远离请求值时仍保留 seekTarget,导致内部目标与现实脱节、后续按键看似无位移。改为 `seeked` 时若 `|currentTime - seekTarget| > 0.75` 则把 seekTarget 重置为实际 currentTime(外部 seek 仍置 null)。
4. **新增当前时间读数** `#currentTimeLabel`(步进输入框右侧,橙色 mono 数字),在 `timeupdate` 里更新 —— 便于用户/我核对每次步进是否精确。CSS `.seek-curtime`。
- 环境限制: `agent-browser` 未安装(需下载 ~500MB Chromium),本轮未做真实浏览器验证,靠代码推理 + 单测;已请用户用新增的当前时间读数复核。
