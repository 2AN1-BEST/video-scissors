## 修复: 上传文件大小上限 (MulterError: File too large)
- 根因: server.js 中 multer `limits.fileSize` 写死 2 GB，用户视频超限，且 /api/upload 无错误捕获 → 抛出原始堆栈
- 修复:
  - 上限改为可配置 `MAX_UPLOAD_GB` 环境变量，默认 10 GB
  - /api/upload 用 `upload.single('video')(req,res,cb)` 包裹，捕获 `MulterError`：
    - `LIMIT_FILE_SIZE` → 413 + JSON `{error:'文件过大，单个视频不能超过 X GB'}`
    - fileFilter 不支持格式 → 400 + JSON `{error:'不支持的视频格式: .xxx'}`
  - 前端 handleFile() 已用 alert 显示 data.error，无需改动
- 验证: node --check 通过；格式拦截返回干净 JSON；独立脚本复现 LIMIT_FILE_SIZE → 413 JSON；主服务(3000)重启后 HTTP 200
- 注意: `parseInt(process.env.MAX_UPLOAD_GB)` 仅认整数 GB，小数会被 `|| 10` 兜底为 10；正常用法传整数(如 20)即可设 20 GB

## 新增: 原画质模式（默认）+ 三种模式可选
- 需求: 用户希望「原画质导出、不做编码」，保留快速/精确可选，且原画质为默认。
- 实现:
  - 前端 index.html: 新增「原画质」模式卡片（radio value=original，默认 checked），三卡并排；style.css `.trim-mode` grid 改为 `repeat(3,1fr)`。
  - server.js `buildTrimArgs()`: original 分支用 `-c copy` 流拷贝（无损、不增大体积、切点对齐关键帧）。
  - 单段原画质 (`/api/trim`): 纯 `-c copy` 无损直切。
  - 多段合并原画质 (`/api/trim-multi`): 纯拷贝拼接会有关键帧漂移/时长错位（实测 2×3s→11.2s），故改用 concat demuxer + `inpoint/outpoint` 单次高质量转码（CRF18，仅一次编码，时长精确、画质接近原片）。
  - 多段分别导出原画质 (`/api/trim-separate`): 纯拷贝会让第二段回退到前一个关键帧导致重叠/时长错乱（实测 8.09s），故 original 在分别导出时按 precise（CRF18）逐段转码，保证各段精确且不重叠。
- 验证（测试视频 10s/1280x720）：单段原画质 h264/aac 拷贝无损、体积按比例；多段合并 6.13s 精确；分别导出 3.00s+3.00s 精确；快速模式回归 6.02s 正常。
- 关键结论: ffmpeg `-c copy` 无法既无损又精确拼接多段，关键帧对齐是硬限制；单段无损可行，多段必须至少一次转码。
